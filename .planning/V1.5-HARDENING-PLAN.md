## 2. New defects found while writing this plan

### 2.0 Unquoted label in the generated Gmail search, driving a destructive action

**This is the most serious item in this document. It is not hypothetical and it is not rare.**

[rules.ts:108](src/modules/rules.ts#L108) builds the search the generated Apps Script runs:

```js
var query = 'label:' + rule.label + ' older_than:' + rule.daysOld + 'd';
var threads = GmailApp.search(query);
```

`rule.label` comes from `tabToGmailLabel`, which returns the raw label name including spaces.
The JS string literal itself is correctly escaped by `escapeForScript`; the defect is one
level down, in the **search grammar**. Gmail splits an unquoted `label:` operator at the first
space:

| Label name | Query produced | Gmail reads it as |
|---|---|---|
| `Receipts` | `label:Receipts older_than:30d` | correct |
| `Old Stuff` | `label:Old Stuff older_than:30d` | `label:Old` AND `Stuff` AND `older_than:30d` |

The second row matches threads that were never in the label. The rule actions are `trash`,
`archive`, `markRead` and `moveToLabel`, so the consequence of a wrong match set is **mail
moved to trash that the user never asked to touch**, on a schedule, unattended.

Multi-word Gmail labels are ordinary. No hostile input is required; a label called
`Old Stuff` is enough. A label containing a deliberate operator (`Foo OR in:anywhere`) widens
it further, which is the injection framing, but the everyday case is already the bug.

Fix: quote the label and escape embedded quotes, i.e. emit `label:"Old Stuff"`. The
`GmailApp.getUserLabelByName(rule.label)` call in the `moveToLabel` branch is an exact-name
lookup, not a search, and is correct as written.

This should ship in the first PR, alongside A2 and E1.

## 3. The compare-and-swap question

### 3.1 What the code actually does today

Every account's settings live in **one** `chrome.storage.sync` key, `account_<email>`, holding
`{ tabs[], rules[], theme, showUnreadCount }`.

Every mutator in [storage.ts](src/utils/storage.ts) is a read-modify-write:

```
addTab / removeTab / updateTab / updateTabOrder / addRule / updateRule / removeRule
   → getSettings(accountId)          // read 1
   → mutate the object in memory
   → saveSettings(accountId, obj)
        → getSettings(accountId)     // read 2
        → { ...current, ...new }     // SHALLOW merge
        → chrome.storage.sync.set
```

Two properties make this worse than a normal lost-update race.

**The merge is shallow.** `{ ...current, ...new }` replaces `tabs` and `rules` *wholesale*.
Two writers touching two completely different tabs still clobber each other. Granularity is
the entire account, not the field.

**There are at least thirteen writers, in two process families.** Not just the options page:

| Surface | Write call sites |
|---|---|
| Options page | [options.ts](src/options.ts) 291, 343, 432, 622, 640 |
| In-Gmail modals | [pinModal.ts:100](src/modules/modals/pinModal.ts#L100), [editModal.ts:97](src/modules/modals/editModal.ts#L97), [deleteModal.ts:75](src/modules/modals/deleteModal.ts#L75), [settingsModal.ts](src/modules/modals/settingsModal.ts) 233/235/301, [importModal.ts:135](src/modules/modals/importModal.ts#L135) |
| In-Gmail drag and drop | [dragdrop.ts](src/modules/dragdrop.ts) 103, 233, 335 |
| In-Gmail tab manager | [tabManager.ts](src/modules/tabManager.ts) 105, 113, 121, 131 |
| Rule templates | [ruleTemplates.ts:158](src/modules/ruleTemplates.ts#L158) |

Every open Gmail tab is a writer. Nine Gmail accounts open means nine content scripts plus
however many options pages.

### 3.2 The sharpest real bug, which is not a microsecond race

[content.ts:319](src/content.ts#L319) subscribes to `chrome.storage.onChanged` and reloads
settings when its own account key changes. **The options page does not.**
[options.ts:831](src/options.ts#L831) filters on `area !== 'local'` and returns, so it only
ever reacts to theme changes. It never hears about `sync`.

So `currentSettings` in an open options page goes stale the moment anything changes in Gmail,
and stays stale indefinitely. Combine that with the reorder paths, which build a tab array
**from the rendered DOM** and write it whole:

```ts
// dragdrop.ts:103, 233, 335 and tabManager.ts:113, 121
await updateTabOrder(getUserEmail()!, tabs);   // `tabs` derived from stale DOM
```

Reproduction, no timing skill required:

1. Open the options page. It renders five tabs.
2. In a Gmail tab, add a sixth tab. Storage now has six.
3. Back in the options page (still showing five), drag to reorder.
4. `updateTabOrder` writes the five-tab array. **The sixth tab is gone.**

That is minutes wide, not microseconds, and it destroys user data. It is the single most
valuable thing in this plan to fix, and it does not need a CAS to fix.

### 3.3 Options considered

### Table H3: Compare-and-swap approaches

| # | Approach | Closes in-browser races? | Closes cross-device? | Cost | Verdict |
|---|---|---|---|---|---|
| 1 | `rev` counter + read-verify-write with retry (optimistic concurrency) in `storage.ts` | Narrows to microseconds, never zero | No | S | Adopt, as the fallback layer |
| 2 | Serialize every write through the MV3 service worker, one promise chain per account key | **Yes, completely** | No | M | **Adopt, as the primary path** |
| 3 | `navigator.locks` Web Locks API | No, see below | No | S | Reject |
| 4 | Re-shape storage: one key per tab, plus an order index | Mostly, structurally | **Yes** | L | Defer, see 3.5 |

**On option 3.** Web Locks is partitioned by storage key, i.e. by origin. Extension pages are
`chrome-extension://<id>`; content scripts run in an isolated world but against the *page's*
document, so their lock scope is `https://mail.google.com`. A lock taken by a Gmail content
script is therefore invisible to the options page, which is precisely the pair we need to
serialize. [Unverified] — this is the documented partitioning behaviour and I am confident in
it, but I have not run it in this extension. Task A1 is a 30-minute spike to confirm. The
recommendation does not depend on the answer: even if locks did span both, option 2 is
simpler to reason about and needs no lock discipline at thirteen call sites.

**Why option 2 works.** The MV3 service worker is a single JavaScript context. Keeping
`queues: Map<accountKey, Promise<void>>` and chaining each mutation onto its account's promise
gives strict serialization by construction, with no lock, no retry and no window. Writers send
a *mutation function's intent*, not a finished object, so the mutation is always applied to a
value read microseconds earlier inside the worker.

Service-worker termination is not a hazard here: the worker only sleeps when nothing is in
flight, and an incoming `sendMessage` wakes it and keeps it alive for the response.

### 3.4 Recommended design

A single new entry point in `storage.ts`, replacing all thirteen call sites:

```ts
export async function mutateSettings(
    accountId: string,
    mutate: (current: Settings) => Settings | void
): Promise<Settings>
```

Three layers, in order of preference at runtime:

1. **Service worker (primary).** `chrome.runtime.sendMessage({ action: 'MUTATE_SETTINGS', accountId, op })`.
   The worker applies `op` against a fresh read inside its per-account queue and returns the
   new `Settings`. Because the op crosses a message boundary it must be **data, not a closure**:
   a small tagged union (`addTab`, `removeTab`, `updateTab`, `reorderTabs`, `setPrefs`,
   `upsertRule`, `removeRule`, `mergeImport`) rather than an arbitrary function.
2. **In-context optimistic CAS (fallback).** When messaging fails (worker unavailable,
   extension context invalidated mid-navigation), apply the op locally: read, check `rev`,
   write `rev + 1`, re-read and confirm; retry up to 3 times with a few ms of jitter, then
   surface a real error to the caller instead of a silent overwrite.
3. **`rev` field on the stored object.** `Settings.rev?: number`, absent meaning 0, so no
   migration is needed. It costs a handful of bytes and makes both a stale write and a
   cross-device divergence *detectable* even where they cannot be prevented.

`reorderTabs` takes an **array of tab ids**, not an array of tab objects. Applied against a
freshly-read `tabs`, an id list reorders what exists and ignores ids that no longer do, so the
stale-DOM scenario in 3.2 becomes impossible rather than merely unlikely. Ids the caller did
not know about are appended in their existing relative order.

And the cheap half of the fix, independent of all of the above: **the options page must
subscribe to `sync` changes for its own account key** and re-render.

### 3.5 What this does not fix, stated plainly

`chrome.storage.sync` replicates through Chrome Sync, which resolves conflicts per key as
last-writer-wins with no hook for us. Two devices editing the same account offline will still
lose one side's edit on reconvergence. Nothing in options 1 to 3 changes that; only option 4
(per-tab keys) does, by shrinking the conflict unit from "the whole account" to "one tab".

Option 4 is deferred rather than rejected, and the reason is quota. Documented
`chrome.storage.sync` limits: 512 items, 8,192 bytes per item, 102,400 bytes total, and 120
write operations per minute. Per-tab keys turn one 10-account profile into roughly 150 to 200
items, which fits, but a single drag-reorder would then write many keys at once and can breach
the per-minute write quota. Note the current shape has its own ceiling: one account's entire
settings must fit in 8,192 bytes, and `saveSettings` has no quota-exceeded handling beyond
rejecting. Worth a measurement before v2.

## What the plan did not predict

Five defects surfaced during the work, all more serious than several planned items:

1. **`applyOp` had no default case.** An op kind this build did not recognise fell off the
   switch, returned `undefined`, and the write path spread that over the account, erasing
   every tab and rule. Ops cross a message boundary, so a Gmail tab on an older build
   talking to a just-updated worker reaches it. Found by a test written for something else.
2. **A second Apps Script comment breakout**, in the header rather than the rule list. The
   account id was escaped for a string context and placed in a comment context.
3. **Stored XSS via an imported backup.** A tab id went unescaped into a `data-tab-id`
   attribute; import validation checked the id was a non-empty string but never its content.
4. **Four more unescaped interpolations** beyond that id, found by turning the guard on.
5. **A deleted tab left its rule** in sync storage forever.

## The InboxSDK finding

Not in the plan, not fixed, and the largest single thing in the codebase.

`@inboxsdk/core` is roughly 1.03 MB of the 1.09 MB content script. Its page-world half has
**never initialised in this extension**, because injecting it needs `chrome.scripting` and
that permission is not in the manifest; it logs an error on every Gmail load.

Both features it provides are already covered by code we own: email detection by
`extractEmailFromDOM()`, and route changes by the body `MutationObserver` plus `popstate`.

Measured, not assumed. A build with the dependency stripped:

| | With InboxSDK | Without |
|---|---|---|
| `content.js` | 1,086,786 bytes | 54,600 bytes |
| Bar ready, fast link | 3,554 / 3,481 ms | 2,707 / 3,244 ms |
| Bar ready, regular 3G | 3,401 ms (tabs not yet drawn) | 3,240 ms (tabs drawn) |
| Active tab follows clicks and hash changes | yes | yes |
| Console errors from us | 1 per load | 0 |

On a fast link the timing difference is inside the noise; the honest headline is the 95%
size reduction and the removal of a dependency whose page world does not run.

Re-verified live on 2026-09-21, in a signed-in Gmail tab with the unpacked build loaded:

```
data-inboxsdk-script-injected     "true"    <- our content script did ask
data-inboxsdk-user-email-address  null      <- pageWorld.js never ran
window.__InboxSDKImpLoader        undefined
console error: Couldn't inject pageWorld.js. Check that the extension is using MV3 and
               has the correct permissions and host_permissions in its manifest.
```

The static chain explains it exactly. `InboxSDK.load()` returns `driver.onready`;
`onready` is `pageCommunicatorPromise.then(...)`; that promise comes from `injectScript()`,
which resolves only once `document.head` gains `data-inboxsdk-user-email-address`, and only
`pageWorld.js` ever sets it. Without the `scripting` permission the SDK's own background
handler answers `false` and nothing is injected, so the promise **never settles** — it does
not reject either, which is why `loadInboxSDK()`'s `catch` has never fired and the failure
has been silent apart from one console line.

So the two features are not merely redundant: `sdk.User.getEmailAddress()` and
`sdk.Router.handleAllRoutes()` have never executed in any shipped build. The email fallback
in `content.ts` is dead code that cannot run, and the unit tests that appear to cover it
(`test/content.test.ts`) mock `load()` to resolve, so they exercise our glue against a
library behaviour that does not occur in production.

Still not done here, because it is a product decision and the removal deserves its own
release: deleting the import also deletes the (non-functioning) email fallback, so the
change should ship with a soak on a profile where DOM extraction is slow.
